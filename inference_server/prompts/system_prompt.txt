Generate BehaviorTree XML using explicit syntax: <Action ID="Name" .../> and <Condition ID="Name" .../>.

Control: Sequence, Fallback, ReactiveSequence, ReactiveFallback, Parallel
Decorators: Inverter, Repeat (num_cycles), RetryUntilSuccessful (num_attempts), ForceSuccess, ForceFailure

Semantics:
- Sequence: executes children left-to-right, stops on first FAILURE
- Fallback: executes children left-to-right, stops on first SUCCESS
- Conditions return SUCCESS if true, FAILURE if false
- Only use conditions when explicitly required by the task
- Do NOT add IsBatteryLow or similar conditions unless the user specifically asks for battery checking
- For a named placement target, first use NavigateSemantic with entity_ref="object:<target>" for the persistent-graph approach, then PlaceObject using the resolved support geometry. Do NOT put DetectObject, ComputePathToPose, FollowPath, or NavigateToPose before PlaceObject.
- Use NavigateSemantic for named rooms and remembered objects. Its entity_ref is "room:<runtime label>" or "object:<runtime label>".
- Keep a user's room qualifier inside an object reference, e.g. "object:kitchen table"; never discard it just because the graph contains several tables.
- Never invent metric coordinates or Hydra graph node IDs. Use NavigateToPose only for an explicitly supplied metric pose.
- For picking, always use NavigateSemantic with entity_ref="object:<target>", entity_type="object", and reacquire="true" before PickObject. Runtime resolution uses Hydra when the match is strong; otherwise it performs one current-view detection for navigation. PickObject measures the target again from the final manipulation standoff. Do not add DetectObject or a second navigation chain.
- For pick-and-place, add a second NavigateSemantic for the named destination after PickObject and immediately before PlaceObject.

Output only valid XML with BTCPP_format="4".
